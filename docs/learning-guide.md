# Learning Guide · 学习方法与内容维护

> **2026-11-04 更新** · 每三天发布一篇深度技术文章。**每篇只有一个主题**，在同一篇中讨论 On-prem / Self-hosted 和 Controlled Hybrid 两种实现路径。

## 五步阅读法

1. **先看筛选过程**。严格优先级为：职业迁移价值 > 技术实质 > 新鲜度 > 可核实的社区反馈 > 是否当天发布。核对原始来源和发布日期；保存 3–5 个最强候选的入选和落选理由。
2. **再看 [知识星图]({{ '/knowledge-graph.html' | relative_url }})**。点击文章，找到它的概念节点与旧文章的依赖、对照或互补关系。优先补齐 prerequisite，而不是囫囵吞新概念。
3. **打开该篇的交互架构图**。切换基线/优化、正常/故障或本地/混合两种以上视图，点击每个组件辨认职责、输入输出、上游下游与权限/失败边界。
4. **读研究正文**。明确区分作者论文中的实验报告、本站的工程推导与未验证的假设；对照算法、资源、模型/引擎版本、测试数据、成本和许可证。
5. **做 30–60 分钟实验并回连图谱**。不依赖外部闭源 API；从小规模可复现的对照与失败注入开始，完成后记录哪些观点被验证、哪些仍待确认。

## 技术关系分类

图谱有五类节点：**article**（单篇研究）、**concept**（核心机制）、**skill**（AI Engineering 求职能力）、**deployment**（On-prem/Controlled Hybrid）、**guide**（学习方法）。采用稳定 ID 和语义边：

| 边类型 | 解释 |
|---|---|
| explains | 研究文章深入解释某个技术概念 |
| prerequisite | 理解目标前需要先掌握来源概念 |
| extends | 文章/方法进一步扩展某个旧问题 |
| complements | 两种机制职责不同但可以协同 |
| shares-core-problem | 两者由相同的工程问题驱动 |
| supports-skill | 研究材料支持某类系统能力 |
| deploys-to | 主要部署讨论路径 |
| guided-by | 受学习与证据审查方法指导 |

**不能因为有一个相同关键词就连线。** 每条边必须写 `reason`，解释工程联系。维护数据源：[`docs/data/knowledge-graph.json`]({{ '/data/knowledge-graph.json' | relative_url }})。

## Guide 更新之前的全库检查门槛

任何新的学习 Guide、选题方法论、术语体系或图谱分类规则一旦准备更新，应当先：

- 枚举 `docs/notes/` 下**全部历史文章**，检查 metadata、来源、日期、引用、术语、旧格式是否适配新 Guide；
- 核查每篇文章是否具有可到达的交互架构图；检查正反向导航、首页/归档入口和图谱数据映射；
- 检查 Graph JSON 的唯一节点 ID、边端点、type、reason；每个新 article 必须与至少一个有真实依据的旧节点相连，不能留孤立文章；
- 针对 Guide 改变的知识点执行**影响分析**：需要同步更正的旧文章和旧交互图应一并修改；不需更改时明确理由；
- 写出公开的变更审计，包括检查范围、实际发现、已修复项、未完成的验证及下一步。

如果只是新研究深化旧问题，可以先更新旧文章及其关联，避免制造重复文章。不得把重新编写的历史稿件冒充旧聊天逐字记录。

## 与 FlowMind 的关系

本学习库的点线图参考 [FlowMind · 念流](https://ljrirene.github.io/flowmind/) 的交互体验：节点、连线、平移、缩放和点击查看关联。两者**是独立应用和独立仓库**。

FlowMind 的个人念头存在用户自己的浏览器中；此公开技术图谱仅使用自有 GitHub 仓库里的公开 JSON，不读取 FlowMind 的 localStorage、不调用它的私人 AI 设置，也不自动同步任何个人数据。

## 研究边界与核查

任何来自论文和供应商的 benchmark 应明确标注来源与范围，不能宣称为本地实测。图谱中 typed edge 表示编辑者基于公开资料建立的工程联系，而非因果已经独立验证。严禁上传私人、公司内部或需要特殊许可的数据。
