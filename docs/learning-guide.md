# Learning Guide · 学习方法与内容维护

> **2026-11-04 更新** · 每三天发布一篇深度技术文章。**每篇只有一个主题**，在同一篇中讨论 On-prem / Self-hosted 和 Controlled Hybrid 两种实现路径。

## 五步阅读法

1. **查看概要和选题依据**。首页、归档与每篇正文会告诉你“它解决什么问题”和“学到什么”，然后再看筛选过程。严格优先级为：职业迁移价值 > 技术实质 > 新鲜度 > 可核实的社区反馈 > 是否当天发布。核对原始来源和发布日期；保存 3–5 个最强候选的入选和落选理由。
2. **再看 [知识星图]({{ '/knowledge-graph.html' | relative_url }})**。点击文章，找到它的概念节点与旧文章的依赖、对照或互补关系。优先补齐 prerequisite，而不是囫囵吞新概念。
3. **查看原理对照图**。先看一个具体问题，以及常见做法和研究方案的差异；点击关键步骤了解工作原理，再看适用范围和代价。完整系统架构、源码与失败条件留在研究正文。
4. **读研究正文**。明确区分作者论文中的实验报告、本站的工程推导与未验证的假设；对照算法、资源、模型/引擎版本、测试数据、成本和许可证。
5. **做 30–60 分钟实验并回连图谱**。不依赖外部闭源 API；从小规模可复现的对照与失败注入开始，完成后记录哪些观点被验证、哪些仍待确认。

## 查看相关文章

关联阅读会说明两篇文章的技术联系。例如 ReplaySSM 减少循环状态写回，Paged Experts 管理 MoE 专家权重分页；两者分别优化不同的数据搬运成本。

首页、归档和正文导读来自统一的 `docs/_data/studies.yml`，包含两句介绍及一两篇精选关联阅读。每个精选链接必须能找到实际文章、知识图谱的文章间连线和一个具体的关系理由。新增研究或更新学习 Guide 时，需要同步检查全部旧导读、链接和知识关系，避免三处描述不一致。

## 技术关系分类

图谱有五类节点：**article**（单篇研究）、**concept**（核心机制）、**skill**（AI Engineering 求职能力）、**deployment**（On-prem/Controlled Hybrid）、**guide**（学习方法）。采用稳定 ID 和语义边：

| 边类型 | 解释 |
|---|---|
| explains | 研究文章深入解释某个技术概念 |
| prerequisite | 理解目标前需要先掌握来源概念 |
| extends | 文章/方法进一步扩展某个旧问题 |
| complements | 两种机制职责不同但可以协同 |
| shares-core-problem | 两者由相同的工程问题驱动 |
| supports-skill | 研究材料支持某类系统能力 |
| deploys-to | 主要部署讨论路径 |
| guided-by | 受学习与证据审查方法指导 |

**关系标签是给系统维护用的分类，而不是给读者的答案。** 页面上应优先显示具体联系，并告诉读者应该先读哪篇、怎样合起来理解。不能因为有一个相同关键词就连线。 每条边必须写 `reason`，解释工程联系。维护数据源：[`docs/data/knowledge-graph.json`]({{ '/data/knowledge-graph.json' | relative_url }})。

## Guide 更新之前的全库检查门槛

任何新的学习 Guide、选题方法论、术语体系或图谱分类规则一旦准备更新，应当先：

- 枚举 `docs/notes/` 下**全部历史文章**，检查 metadata、来源、日期、引用、术语、旧格式是否适配新 Guide；
- 核查每篇文章是否具有可到达的原理对照图；检查正反向导航、首页/归档入口和图谱数据映射；
- 检查 Graph JSON 的唯一节点 ID、边端点、type、reason；每个新 article 必须与至少一个有真实依据的旧节点相连，不能留孤立文章；
- 针对 Guide 改变的知识点执行**影响分析**：需要同步更正的旧文章和旧交互图应一并修改；不需更改时明确理由；
- 写出公开的变更审计，包括检查范围、实际发现、已修复项、未完成的验证及下一步。

如果只是新研究深化旧问题，可以先更新旧文章及其关联，避免制造重复文章。不得把重新编写的历史稿件冒充旧聊天逐字记录。


## 问答式学习（无 API）

[**Study QA：向知识库提问 + 主动回忆**]({{ '/study-qa/' | relative_url }})

- **向知识库提问**：在浏览器内查找全部研究的相关文本片段，显示文章名称、章节与原文链接。不会把检索片段假装成模型生成的完整结论。无需模型、外部 API Key 或服务端后台。
- **主动回忆**：针对每篇文章维护至少 2 道人工校验过的机制/系统设计题，先自己回答，再看提示、概念覆盖与参考答案。关键词覆盖仅为学习提示，**不能证明答案在语义或逻辑上正确**；回答与进度仅存在当前页面会话。
- **有新文章时**：核查所有既有研究、更新 `docs/data/study-corpus.json` 并新增 2–3 道针对新研究的问题到 `docs/data/study-questions.json`；保持文章稳定 ID、URL 和概念关系一致；新增 Guide 时按上面的全库门槛审查所有旧题。
- **AI 导师的扩展**：真实动态苏格拉底式追问、语义评分或跨文档自然语言总结需要接入本地自托管 LLM（如 Ollama）或托管 API。若未来公开部署此功能，不得把服务商付费 API Key 写入 GitHub 静态前端；需要受认证的后端 Proxy 或用户明确选择的本地模型，并遵守数据出域限制。

FlowMind 的私人浏览器存储不在公开检索索引中。任何未来接入必须是用户主动导入/授权，不可擅自读取或同步个人数据。

## 与 FlowMind 的关系

本学习库的点线图参考 [FlowMind · 念流](https://ljrirene.github.io/flowmind/) 的交互体验：节点、连线、平移、缩放和点击查看关联。两者**是独立应用和独立仓库**。

FlowMind 的个人念头存在用户自己的浏览器中；此公开技术图谱仅使用自有 GitHub 仓库里的公开 JSON，不读取 FlowMind 的 localStorage、不调用它的私人 AI 设置，也不自动同步任何个人数据。

## 研究边界与核查

任何来自论文和供应商的 benchmark 应明确标注来源与范围，不能宣称为本地实测。图谱中 typed edge 表示编辑者基于公开资料建立的工程联系，而非因果已经独立验证。严禁上传私人、公司内部或需要特殊许可的数据。
